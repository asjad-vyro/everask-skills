# Responding to reviewers

Use this for rebuttals, response letters and revision notes to an editor. The goal is a response that answers every point, is honest about what changed, and makes the editor's decision easy.

## Before you write

1. Number every comment (Reviewer 1, comment 1.1, 1.2, ...) in the order given. Split a long paragraph into its separate requests.
2. Sort each comment:
   - **Must fix**: it affects validity or points to missing evidence (a missing baseline, an unsupported claim, a flaw in the design).
   - **Clarity**: the reviewer misread, or the text was unclear. Fix the text.
   - **Cannot do**: out of scope, impossible, or in conflict with another reviewer. Say why, and say what you did instead.
   - **Disagree**: the reviewer is mistaken. Explain with evidence, politely.
3. Note comments that several reviewers share. Answer once in full, then point back to that answer.

## Shape of the response letter

1. **Opening** (short): thank the editor and reviewers in one plain sentence, then list the main changes as three to five bullets.
2. **For each reviewer, each comment in turn**:

   > **Comment 1.1**: the comment, quoted exactly (shortened with "[...]" only if very long).

   **Response**: the answer.
   **Change**: what changed in the manuscript and where (section, page or line number if the user gave them, otherwise `[section]`), with the new or revised text quoted when it is short.
3. Keep the reviewers' order and numbering so the editor can follow along.

## How to write each response

- Answer the question the reviewer asked in the first sentence ("We agree...", "We have added...", "We respectfully disagree because...").
- Concede points that are right, plainly and without grovelling. Agree wherever you honestly can.
- Where you disagree, give the reason and the evidence (data, a citation the user supplied, a passage in the manuscript). Still offer a change that makes the point clearer in the text: a misunderstanding usually means the text was unclear.
- Be specific. "We added the comparison with [named baseline] in Table 3" beats "We have improved the evaluation".
- **Never claim a change the user has not made or you have not drafted.** Write each change as one the user will make, and supply the new text so they can paste it.
- **Never invent results.** If a reviewer asks for an experiment, analysis or data the user has not given you, do not report an outcome. Write the response around what will be done and leave `[insert result: ...]` where the outcome goes.
- Do not promise what the user did not say they would do (new data collection, a new study).
- Do not argue about tone and do not answer a hostile comment with hostility; respond to its substance.
- Quote the user's manuscript text exactly, unless the response is proposing new text.
- If the user gave the reviewer comments but not the manuscript, write the responses from what the user told you, and put `[section/page]` where a location is needed.

## Rebuttal with a length limit

When the venue sets a word or character limit (common for conference rebuttals): spend the words on the points that could change the decision (validity, missing evidence, misreadings that lowered a score), answer minor points in a line each or group them, and put the strongest answer first. Count the words with `execute_code` and state the final count.

## After a rejection (resubmitting elsewhere)

Do not just patch each comment. Ask what the paper claims to be about and whether the evidence supports that claim. If the comments show a mismatch, the next version needs a rewrite of the argument, not a polish of the sentences. Say this in the closing notes.

## Closing notes (after the letter, in your reply)

List: each place where the user must supply a result, a page or line number, or confirm that a change was made; any comment you could not answer from the material given; and every assumption you made.
